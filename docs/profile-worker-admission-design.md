# Profile-bound worker admission: implementation boundary

Base: 93e4fcd3. This worktree has an unreviewed experimental implementation of part of the chain below. The v2 Hub and worker interlocks are hard-disabled; baseline v1 remains available and retains its existing authorization and limitations. This does not establish staging readiness.

## Behavior at the base revision

- `StagingController.submit` persists source provenance and a project/recipe name; `WorkTarget` carries a source and review revision but no profile tuple. Both controller and `WorkQueue._modular_target_in_transaction` use the ordinary `reviewed_task_matches`, which deliberately rejects tasks with profile bindings. Do not remove that rejection without a complete replacement.
- Worker `Service.submit` accepts legacy source-only payloads, reads its configured recipe to size a reservation, and `_execute_operation` independently looks up the recipe again. `profile_digest` is merely optional in HTTP result validation. No current result proves which execution profile ran.
- The submission journal and queue target are separate persisted snapshots. Worker operation identity hashes its input; accepted/running operations recover as held. Existing reconciliation checks the original operation and ownership. A missing digest on an older operation is not evidence of a matching profile or that it is safe to replay or release.

## Required closed transition

1. Resolve the task's current independently approved owner-enrolled `(project, recipe, generation, digest)` within the same Hub writer transaction as submission insertion. Validate candidate, review revision, reviewer lineage, enrollment canonical bytes, project, and generation. Do not trust a tuple or digest asserted by the requester. Persist the exact tuple in the submission's idempotency fingerprint. Reuse the existing review lineage checks without weakening the generic commit-only rejection.
2. Require the exact persisted tuple at every queue submit/claim/pre-dispatch transaction. Match it to the current reviewed task and source proof and the configured action; revoke or change before worker transmission must stop admission. Update the controller verifier and transactional queue verifier together. Any absent or inconsistent tuple denies new dispatch; legacy retained records cannot be silently upgraded.
3. Define a versioned worker request which includes the Hub-derived tuple and original source binding. Require it for v2 staging dispatch, rejecting name-only or malformed v2 requests before any reservation or side effect. V1 remains a separate, existing path and must not be selected as an automatic fallback for a v2 task. The worker computes the digest of the exact effective locally configured recipe using the shared closed canonical format, compares it to the Hub digest, and rejects mismatch before reservation. A name or echoed caller digest is not a proof.
4. Deep-copy the effective recipe, canonicalize and verify that copy, and use that same detached value for reservation and backend execution. The current experimental snapshot occurs before the worker admission lock; a reviewed configuration-generation authority is still needed to fence concurrent or cross-process replacement. Do not re-read `self.projects` during v2 execution. Persist the tuple in the worker operation payload and bind it into the identity and terminal receipt, including successful and definitive failed receipts. Validate packaging: the worker must have the exact canonicalization implementation, independent of the Hub service process.
5. At Hub follow/finalization and held reconciliation, require the original tuple/digest to match the persisted submission and worker terminal proof before any success/failure finalization or release. A missing, contradictory, or unknown proof holds the original operation and resources; never synthesize a digest for old records or issue a second POST. Keep the existing source, resource, ownership, terminal consistency, and physical absence checks.
6. Upgrade worker and Hub as a coordinated protocol change. New protocol capability must be confirmed for the precise worker before enabling dispatch. V1 remains available by its existing route and v2 uses separate endpoints; v2 must not fall back to v1. Existing unbound held records stay held and read-only; a separate explicit audited recovery protocol must establish physical absence before release, without attributing a profile.

## Verification before integration

Use real Hub/controller/queue plus worker HTTP/journal integration with a synthetic backend: reviewed tuple succeeds; changed review, candidate, project, recipe, generation, digest, enrollment, and worker recipe fail; mutate the configured recipe after acceptance and demonstrate the snapshotted original is used; reject name-only messages and fail closed on old worker; exercise idempotency conflict, restart, lost POST response, and held reconciliation without repost; missing/mismatched digest on success and failure preserves reservation; exercise policy revocation and queue races. Verify actual worker package and protocol versions. Run independent security review and required existing tests. These are synthetic tests, not real pilot or host isolation evidence.

## Unfinished installation-session admission and protocol rollout

The synthetic end-to-end test currently uses legacy family actors. `staging_api` and the controller explicitly reject installation actors, and the session Hub bridge exposes only synchronous capabilities under a session SQLite writer. Do not replace these checks with an `installation:` prefix check or hold that writer across source verification, remote source deposit or worker dispatch.

A separate design and review must specify an explicit owner-granted staging-submit capability scoped to the project; exact installation, original session, family, authorization revision and expiry; session-to-Hub lock ordering; a durable admission record committed with the exact reviewed tuple and audit provenance; and how revocation, expiry, changed project access and session replacement affect source deposit and later dispatch. The exact originating claim session must be checked, not just installation or family. Recheck authorization at each irreversible admission boundary without storing bearer secrets or awaiting remote calls while holding the session writer. Define crash recovery, idempotency and cancellation for a committed intent whose session expires or is revoked before/after a remote effect. A historical admission is not automatically present-day execution authority. Add deterministic revocation/expiry ordering tests and independent review before exposing this path.

Both v2 gates remain false. The v1 routes continue to use the existing worker credential, and a holder of that credential may directly invoke v1 even if v2 is enabled. Hub-side route selection is therefore not receiver-enforced downgrade protection against that holder; separate credentials or a receiver-enforced v1 retirement policy need design and review. The v2 status and source/job routes are separate from v1; this is not independently fenced endpoint identity or an epoch binding, and a status check cannot fence worker replacement between checks.

Before a v2 source POST the Hub records `deposit_unknown` with the original source identity. A lost response, interruption or restart holds that intent and never automatically reposts it. There is currently no authorized read-only original-source resolution path and no authenticated worker-ledger epoch, so the hold has no safe automatic release: a missing response from a replacement or restored worker is not evidence of absence on the original. The local transaction rechecks review and project build/test policy before intent; an intent that commits first is not invalidated by a subsequent revoke, and is not an external effect fence. A complete solution needs coordinated pending revocation/drain, a receiver-enforced epoch and independently protected host/rollback authority, followed by tests of both orders and crash recovery. No SQLite writer may be held across network I/O.

The standalone synthetic worker wheel and mixed-version local tests qualify only the exact experimental artifact and test environment. They do not establish authenticated endpoint custody, current installed-host behavior or production acceptance. Installation-owned EHS submissions remain unsupported until the synchronous session-to-Hub admission and durable dispatch authority are implemented; do not weaken the actor check.
