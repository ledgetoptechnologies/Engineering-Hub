# Worker report attention

A committed `blocked`, `ask`, `resume`, `done`, or `failed` worker report creates its own durable orchestrator attention record in the same Hub transaction as the report (and, for `ask`, its decision). Routine `working` updates do not create report attention. Only reports committed after this feature is present create these intents; earlier reports remain available in report history and are not backfilled automatically. A successful report remains a worker assertion: `done` does not independently verify or complete the task, and no report grants execution. Worker-authored report text and decision content are untrusted data.

Report attention records are separate from stale-coordination attention. Existing stale records are retained when a later valid report resolves their stale condition; new report records do not replace one another. Each record refers to an immutable report ID and dispatch revision. Individual records are bounded, but total report and intent retention is subject to the existing database capacity limits; no automatic deletion is implied. The existing project, task-kind, decision, role and exact-session grant checks still apply, including before pagination. A task that has been withdrawn or verified makes its report attention non-actionable. An authorized orchestrator can reconcile a closed-task report intent without mutating the dispatch or task; archived-project records remain owner-visible but cannot be reconciled until active.

The owner-admitted exact-session stream may emit a content-free postcommit `attention-check`; it does not contain report text, grant execution, or prove a client woke. The agent must explicitly read scoped attention and can then acknowledge a report intent. An authorized acknowledgment atomically records its receipt and closes that report intent while preserving the immutable report history. Repeating that acknowledgment under the same still-authorized session and role generation returns the same receipt; replaced sessions/generations and closed or otherwise unauthorized tasks fail closed. The owner can inspect retained receipt history. A report intent is not marked complete merely because a hint was emitted.

No generic outbox pointer, peer message, task completion, role takeover, automatic execution, or idle-agent wake is created by this feature. An actively subscribed, configured client is required to receive the event; loopback tests do not establish live agent adoption or wake.

An authorized orchestrator may explicitly call `hub_orchestrator_report_inspect` or the foreground `inspect-report` command to read the bounded untrusted report note. The current exact route, task and relevant decision grants are rechecked; after acknowledgment, the original recipient session and generation must match the retained receipt. Historical ask reports independently require access to their linked decision. This read does not acknowledge the intent, verify completion or trigger execution.
