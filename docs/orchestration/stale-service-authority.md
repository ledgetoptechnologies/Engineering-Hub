# Scoped stale evaluation authority

The owner-only stale-service grant is disabled when absent. An authenticated owner can authorize a bounded set of active projects for a limited lifetime on a ledger held by its exact live `PilotOwner`; revocation and updates use revision checks. This grant alone remains inert: its `scheduler: not_installed` value describes the grant, and it does not enable evaluation. It permits no execution, deployment, inbox polling, message delivery or agent impersonation.

A separate owner-only, CSRF-protected `PUT /api/hub/v1/orchestration/stale-evaluator` explicitly enables the advisory evaluator for the current grant revision. `GET` reports its configuration, worker state and errors. The process-owned evaluator checks a bounded round-robin set of dispatch records. Its timing is best effort and backlog size affects latency. It first records a private, boot-bound observation of the dispatch, task, role, claim and progress. An unchanged observation must age for the full report window plus four seconds before a timeout, so a legacy dispatch may wait an additional window. Anchors survive grant renewal within the same owner epoch and boot. Ambiguous target lease or authorization loss waits at least 3604 seconds of unchanged observation and four seconds of confirmed loss; a shorter grant can expire before this indication is possible. Records whose JSON cannot be attributed to a scoped project are skipped without a global corruption diagnostic. An absent opt-in does no evaluation. A service admission failure conservatively requires a fresh grant. If a target role references an archived or unavailable project, that dispatch is skipped and the owner sees a generic role-unavailable diagnostic; evaluation continues for other eligible dispatches. A new Hub app instance requires a freshly approved service-grant revision and fresh opt-in; an old stored opt-in never starts a new instance. Disabling waits for the owned worker to exit.

The evaluator serializes session revocation with the session writer before acquiring the Hub writer. It checks the service grant, project, emergency pause, current task, dispatch, role, target session and lease, and attributable progress before applying the existing advisory checkpoint transition. Stale records and pending attention intents do not mean a process stopped, work failed or was replayed, a task was verified, or anyone was notified. Each automatic stale intent retains bounded timing and state-digest evidence for review. The digest is locally computed, not independently signed provenance or proof of delivery or that a worker stopped. No generic outbox pointer is published and there is no sender, recipient mapping or verified wake.

The grant and evaluator bind the exact Hub repository, PID, live owner lock and owner epoch. Reboot, owner-epoch change, a clock fault or evaluator reconstruction requires fresh owner approval. Evaluation compares wall time, session time and suspend-aware Linux `CLOCK_BOOTTIME`; unsupported or inconsistent clocks fail closed. Clock checks are sampled and cannot prove a clock did not jump between observations. Grant, clock, lease and owner checks run before the repository's final owner/context checks and SQLite commit. This is a cooperative precommit check: a blocked synchronous commit can outlast its deadline and cannot be interrupted as a strict real-time fence.

The component is not a sandbox against hostile code already inside the Hub process. This configuration does not establish a private Engine, host worker isolation, staging admission, automatic message delivery or agent wake. It does not poll an AI inbox.
