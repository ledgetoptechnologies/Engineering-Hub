# Shared staging execution policies

This is a private source integration boundary, not joint pilot enrollment or an activated application mode. The application's existing executor-conflict guard remains in place. No new owner, database, machine alias, credential, listener or Docker endpoint is created.

`SharedExecutionPolicies` binds the exact repository and canonical `WorkQueue` to disjoint action families, fixed workers and synchronous target/claim/completion/reconciliation handlers. It snapshots action values, handler identities, queue callbacks, approval authority and global readiness authority. Unknown actions, callback replacement and binding drift deny admission; a missing claim callback cannot restore standalone admission semantics after shared installation.

Construction and binding do not install queue callbacks. Explicit installation leaves admission closed. Opening requires all expected families to be bound and ready, every snapshot action to be covered, and existing reservations to have known family/machine bindings. A reservation whose family is absent raises `foreign_hold_family_absent`; this audit never adopts, reconciles or releases it. Marking a family ready is a trusted composition step, not independent proof that its recovery completed.

Closing admission is terminal for that registry instance. New claims, source uploads and job/cleanup dispatch stop. Intact original completion/reconciliation remains available. Stored job identity, action, worker and fence determine proof routing; a caller cannot redirect evidence into another family. Live completion requires the exact current worker instance. After restart, reconciliation routes the validated original worker to its own executor family without requiring the new instance to equal the old one. The family's verifier still authorizes the original command/journal and, for the pilot, excludes the prior owner epoch. This routing neither rewrites ownership nor grants recovery by itself. A read-only claim plan is rechecked against the current barrier when claimed.

Shared-mode production priority covers the physical machine before worker/action filters. A target-policy denial is not global unavailability. Unknown, unbound or malformed production bindings/approval/readiness retain the barrier. An intact binding with trusted approval exactly `False` establishes revocation; trusted global readiness exactly `False` establishes unavailability for an approved bound row. Neither grants production execution. Standalone queue behavior remains unchanged.

`StagingController(..., execution_policies=...)` optionally registers its modular actions without replacing the registry callbacks. It checks admission before new effects, and checks original identity after awaited replies before updating local state. Closing admission after acceptance permits original receipt processing; binding drift preserves the original claim for reconciliation rather than authorizing a replacement POST. The repository's execution principal is unchanged and modular jobs create no pilot run entity.

## Remaining joint composition

The real `QueuedContainerPilot` bridge accepts an optional explicit shared binding, preserving its existing owner/epoch/manifest/review/private-permit guards. It registers its family without replacing registry dispatchers. New claim/run/command preparation checks shared admission; original response/proof/recovery paths check the intact binding without requiring admission to reopen. Registry closure during fresh async preparation follows the reconciliation gate's existing fail-closed disposal rule and can close that gate; it does not manufacture a new recovery capability. An already accepted final response can still complete under its valid original gate.

Linux tests exercise both actual controllers on one real `PilotOwner`, repository and physical-machine queue, using simulated remote executor responses. They cover sequential release, cross-family holds and the pilot's existing four-phase failed-health rollback. These are owner/ledger integration tests, not staging-host Docker execution or independent executor attestation.

An explicit private `modular_controller` reference now permits enrollment to recognize a coherent modular reservation inside its existing SQLite transaction. It requires the exact pre-install registry binding, controller/repository/queue context, original queue worker/fence, unique submission and fingerprints, source binding and four resource ownership records. Unknown, inconsistent or ambiguous history retains the enrollment veto. Existing unbound-run checks remain unchanged. No caller-supplied allow callback exists.

The matcher only preserves an existing hold. It performs no writes, expiry, remote call, adoption, replay or release. An unexpired previous worker lease stays unchanged and is skipped by automatic modular recovery. Generated source/command UUIDs are journal assertions, not independent remote attestation: a coherent changed UUID cannot make a mismatched original receipt release the machine. Actual original-receipt and family recovery checks remain authoritative.

History is streamed with limits of 128 KiB per JSON record, 8 MiB total metadata and 10,000 records. Exceeding a limit preserves the veto; history is never silently truncated or pruned. A single SQLite row is necessarily materialized before its size is rejected. These limits bound metadata scanning, not overall Hub memory acceptance.

One application startup composition must still recover both original identities before marking either family ready, and shutdown must drain both clients before releasing the single owner. Starting today's claim loops against a closed registry is insufficient: recovery and admission opening need explicit lifecycle ordering. Owner-facing wait-reason contracts, real joint deployment/rollback acceptance and NAS/app/reboot checks remain separate requirements. Keep the application conflict guard until those requirements pass.
